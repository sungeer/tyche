# 银行投资理财 Agent — 产品需求文档

> 版本：v1.0  
> 日期：2026-04-09  
> 作者：产品 & AI 架构团队

---

## 一、项目背景与定位

### 1.1 背景

银行投资理财部内部人员（理财顾问、客户经理、风控专员、合规审核人员）日常需要频繁查询产品信息、分析客户持仓、评估风险敞口、处理赎回申请。现有系统均为独立系统，人员需要在多个系统间反复切换，效率低下且容易出错。

本项目旨在构建一个**面向银行内部人员的智能 Agent 应用**，以自然语言为交互入口，统一调度后台各数据系统（产品库、持仓系统、风控引擎、合规系统等），将结构化数据转化为可读的业务答复，并全程留存合规审计证据。

### 1.2 定位

- **使用对象**：银行内部员工，非 C 端客户
- **交互方式**：多轮对话（Web Chat 界面），部分操作支持异步审核流转
- **LLM**：银行自建 `Qwen3.5-397B-A17B`，部署在行内私有网络，数据不出行
- **后端**：基于现有 `hostess` 项目扩展，纯 Python 手搓 Agent，不引入 LangGraph / AutoGPT 等重框架

### 1.3 核心目标

| 目标 | 说明 |
|---|---|
| 效率提升 | 一句话完成跨系统查询，替代手动切换 3~5 个系统 |
| 合规留痕 | 每次查询与操作全链路可追溯，满足监管要求 |
| 风险管控 | 基于用户角色和客户风险等级，在 AI 层做前置拦截 |
| 可解释性 | AI 的每个判断有据可查，审计人员可复现 |

## 二、用户角色与权限分层

### 2.1 角色定义

| 角色代码 | 角色名称 | 典型操作 |
|---|---|---|
| `ADVISOR` | 理财顾问 | 查询产品、分析客户持仓、生成配置建议 |
| `MANAGER` | 客户经理 | 上述 + 批量客户分析、赎回申请发起 |
| `RISK_OFFICER` | 风控专员 | 查询风险敞口、压力测试结果、异常持仓预警 |
| `COMPLIANCE` | 合规审核人员 | 审核待批准操作、查看审计日志、操作拦截规则管理 |
| `ADMIN` | 系统管理员 | Skill 管理、用户权限管理，不参与业务操作 |

### 2.2 权限矩阵

| 权限点 | ADVISOR | MANAGER | RISK_OFFICER | COMPLIANCE | ADMIN |
|---|---|---|---|---|---|
| `product:read` | ✓ | ✓ | ✓ | ✓ | - |
| `portfolio:read` | ✓ | ✓ | ✓ | ✓ | - |
| `portfolio:read_all` | - | ✓ | ✓ | ✓ | - |
| `risk:read` | - | - | ✓ | ✓ | - |
| `redemption:initiate` | - | ✓ | - | - | - |
| `audit:read` | - | - | - | ✓ | - |
| `review:approve` | - | - | - | ✓ | - |
| `skill:manage` | - | - | - | - | ✓ |

### 2.3 客户风险等级与产品风险匹配规则

这是 Node 2 合规拦截的核心规则之一，由行内风控规则引擎提供，此处描述业务语义：

- 客户风险等级分为 `R1`~`R5`（R1 最保守，R5 最激进）
- 产品风险等级分为 `PR1`~`PR5`
- **规则**：`客户风险等级 < 产品风险等级` 时，禁止顾问为该客户推荐或查询该产品的客户匹配度
- **例外**：客户本人主动申购且已签署风险承担声明，走人工审核流程

## 三、功能性需求

### 3.1 多轮对话会话管理

**FR-001：会话创建与持久化**
- 用户首次发起对话时，系统创建 `session_id`，并关联当前用户身份
- 会话历史存储在数据库，支持跨请求的上下文连续性
- 单个会话最多保留 **20 轮**（40 条消息）历史，超出时滚动丢弃最早的
- 会话空闲超过 **4 小时**自动关闭，关闭后下一条消息开启新会话

**FR-002：上下文引用解析**
- Node 1 意图识别时，结合历史消息解析代词引用
- 示例："那个产品"、"刚才说的客户"、"上一个结果里" 均需解析为具体实体
- 解析失败时（置信度 < 阈值），主动向用户澄清，不猜测执行

**FR-003：会话状态可见**
- 用户可查询当前会话包含的轮次数量
- 用户可主动发起"清除上下文，重新开始"

### 3.2 意图识别（Node 1）

**FR-010：意图分类**

支持以下意图类别，随业务扩展可新增：

| 意图类别 | 说明 | 示例输入 |
|---|---|---|
| `product_query` | 产品基本信息查询 | "查一下XX货币基金今天的净值" |
| `product_compare` | 多产品对比 | "比较A和B两只基金的近一年收益" |
| `portfolio_analysis` | 客户持仓分析 | "帮我看看张三的持仓结构" |
| `risk_assessment` | 风险评估 | "当前组合在利率上行100bp情景下的损失" |
| `redemption_initiate` | 发起赎回申请 | "帮客户李四赎回XX理财5万元" |
| `audit_query` | 审计记录查询（仅 COMPLIANCE 角色） | "查一下上周有没有R1客户被推荐了R4产品" |
| `small_talk` | 闲聊 / 无关话题 | "你好"、"帮我写首诗" |
| `out_of_scope` | 超出系统能力范围 | "帮我发邮件给客户" |
| `ambiguous` | 意图不明确，需澄清 | 输入过于简短或歧义 |

**FR-011：意图置信度阈值**
- 置信度 ≥ 0.85：正常执行
- 置信度 0.6~0.84：执行但在响应中注明"已按 XX 理解，如有偏差请澄清"
- 置信度 < 0.6：不执行，主动向用户提问澄清

**FR-012：意图拒绝**
- `small_talk` 和 `out_of_scope` 在 Node 1 直接截断，返回礼貌提示，**不进入后续节点**，**不写审计日志**（非业务行为）

### 3.3 合规拦截与 Skill 路由（Node 2）

**FR-020：用户权限拦截**
- 根据当前用户角色，校验其是否有权执行识别出的意图
- 无权限时返回明确提示，写入合规事件日志

**FR-021：客户风险等级拦截**
- 当意图涉及特定客户与特定产品的匹配度查询或推荐时，校验客户风险等级与产品风险等级的合规性
- 接入行内风控规则引擎（HTTP 接口调用），规则结果为准
- 拦截时返回原因，写入合规事件日志，**不写"操作失败"，而是写"合规拦截"**（两者审计含义不同）

**FR-022：人工审核触发条件**
以下场景触发人工审核，流程暂停等待审核人处理：

| 触发场景 | 审核角色 | 审核 SLA |
|---|---|---|
| 赎回金额 ≥ 50 万元 | COMPLIANCE | 2 小时 |
| 客户签署风险承担声明后的越级产品操作 | COMPLIANCE | 1 个工作日 |
| 同一顾问同日内第 3 次及以上访问同一客户全部持仓 | RISK_OFFICER | 4 小时 |

**FR-023：Skill 参数构建**
- 从 Node 1 提取的实体（`entities`）自动映射为 Skill 入参
- 入参在执行前必须通过 JSON Schema 校验，校验失败视为"参数错误"，不调用 Skill

### 3.4 Skill 执行（Node 3）

**FR-030：并发执行规则**
- 同一次请求选中的多个 Skill，若相互无数据依赖，则并发执行
- **Skill 注册表中标记为 `depends_on` 的 Skill 必须串行执行**，不得并发

**FR-031：超时与降级**
- 每个 Skill 有独立的 `timeout_ms` 配置（默认 5000ms）
- 超时后：
  - 若该 Skill 被标记为 `allows_degradation: true`（只读操作），记录超时，用部分结果继续
  - 若该 Skill 被标记为 `allows_degradation: false`（写操作 / 关键数据），整体流程失败，返回服务不可用

**FR-032：写操作的幂等性**
- 所有写类型的 Skill（`write_operation: true`）必须支持幂等调用
- 调用前生成 `idempotency_key`（`turn_id + skill_id`），由 Skill 实现端负责保证幂等
- 重试前必须检查 `idempotency_key` 是否已被执行，防止重复下单

**FR-033：知识库检索（RAG）**
- 在 Node 3 阶段，与业务 Skill 并发执行知识库检索
- 检索基于 ChromaDB 向量数据库，输入为用户原始问题 + 意图关键词
- 检索结果（top-K chunks）随 Skill 结果一同传递给 Node 4

**FR-034：知识库权限隔离**
- ChromaDB 中的文档按角色打标（`allowed_roles` 字段）
- 检索时过滤当前用户角色无权访问的文档
- 例：私行产品说明书仅 `MANAGER` 及以上角色可检索

### 3.5 LLM 响应合成（Node 4）

**FR-040：自然语言生成**
- 将 Skill 返回的结构化 JSON 数据 + 知识库检索 chunk + 对话历史，组装为 prompt，调用 LLM 生成自然语言答复
- 输出必须忠实于结构化数据，不得自行"推断"或"补充"数据中没有的内容

**FR-041：流式输出（SSE）**
- Node 4 采用 Server-Sent Events 流式返回，用户端可逐字看到输出
- 流结束后执行后置校验（FR-042），校验失败时以醒目提示替换输出

**FR-042：数值一致性校验**
- LLM 输出完成后，自动提取文本中的所有数值（百分比、金额、日期）
- 与 Skill 返回数据中对应字段进行比对
- 任何数值偏差 > 0.01% 时，在响应尾部追加警示："⚠️ 数据核对发现差异，请以系统数据为准"，并记录到审计日志

**FR-043：合规用语过滤**
- LLM 输出中禁止出现下列表达（正则匹配，可配置扩展）：
  - `保证收益`、`稳赚`、`一定涨/跌`
  - `建议您购买`、`推荐投资`（顾问工具不可替代投资顾问资质）
  - `保本`（监管明令禁止的承诺）
- 匹配到违规表达时，整段响应不予展示，返回"当前回答包含不合规表达，已被系统拦截"，并写入合规事件日志

**FR-044：无数据时的处理**
- 若所有 Skill 均返回空数据或失败，LLM 不得"编造"内容
- 此场景下直接返回固定文案：系统未查询到相关数据，请确认查询条件后重试

### 3.6 人工审核流转

**FR-050：异步审核机制**
- 触发人工审核时，系统立即向用户返回响应：任务已提交，当前状态：待审核，预计处理时间 XX
- 后台创建审核任务，分配给对应角色的审核人
- 用户可通过 `GET /agent.task.status` 轮询任务状态

**FR-051：审核人操作**
- 审核人通过专属界面（或 Agent 对话）查看待审核任务
- 审核人可执行：**通过**（继续执行 Node 3 残余流程）、**驳回**（返回原因给提交人）、**转审**（升级给更高权限审核人）
- 审核人可修改参数后再放行，修改内容必须完整记录到审计日志

**FR-052：审核超时处理**
- 超过 SLA 时间未处理：系统发出提醒通知（站内消息 / 邮件，具体渠道待定）
- 超过 2×SLA 时间：任务自动升级给上级审核人，原审核人保留记录
- **不支持"超时自动通过"**，所有写类型操作的审核必须有人工确认

**FR-053：审核任务的持久化**
- 审核任务存储在数据库，不依赖内存状态
- 服务重启后，待审核任务自动恢复（不丢失）

### 3.7 审计日志（Node 5）

**FR-060：全链路审计**
- 每次请求（无论成功/失败/拦截）均写入审计日志
- 审计日志与业务数据库**逻辑隔离**（独立表，写操作单独连接），防止业务异常影响审计写入

**FR-061：审计字段要求**
每条审计日志必须包含：

| 字段 | 说明 |
|---|---|
| `run_id` | 本次请求追踪 ID |
| `session_id` | 所属会话 ID |
| `turn_id` | 本轮对话 ID |
| `user_id` | 操作人 |
| `operator_role` | 操作时的角色 |
| `intent` | 识别到的意图 |
| `skills_called` | 调用的 Skill 列表（含入参摘要，PII 脱敏后） |
| `compliance_events` | 合规检查事件（通过/拦截/触发审核） |
| `llm_calls` | LLM 调用次数、token 用量 |
| `node_durations` | 各节点耗时（ms） |
| `final_status` | 最终状态：`completed` / `rejected` / `pending_review` / `failed` |
| `created_at` | UTC 时间，精确到毫秒 |

**FR-062：PII 脱敏规则**
- 审计日志中的客户姓名显示为：张* / 李**（保留姓，名用 * 替代）
- 身份证号显示为：110101\*\*\*\*\*\*\*\*1234
- 账户余额不写入审计日志（仅记录"已查询"，不记录具体数值）
- 手机号显示为：138\*\*\*\*9876

**FR-063：审计日志防篡改**
- 每条审计日志写入时生成 `content_hash`（SHA-256），存储于独立字段
- 审计记录写入后不可更新，只可追加
- 合规人员可通过 `GET /agent.audit.verify` 接口批量验证日志完整性

**FR-064：日志保留期**
- 审计日志保留 **10 年**（依据《商业银行内部控制指引》）
- 业务数据可按需清理，但审计日志不受业务数据清理策略影响

## 四、非功能性需求

### 4.1 性能

| 指标 | 目标值 | 说明 |
|---|---|---|
| 端到端 P95 响应时间 | ≤ 3s（首 token 到达） | 不含 LLM 完整输出时间 |
| Node 1 意图识别 | ≤ 1s | 单次 LLM 调用 |
| Node 3 Skill 执行 | ≤ 5s（单个） | 超时即降级/失败 |
| 并发会话数 | ≥ 200 | 行内员工同时使用 |
| 审计日志写入 | 不阻塞主链路 | 异步写入，主响应不等待 |

### 4.2 可靠性

- 关键节点（Node 2 合规拦截、Node 5 审计写入）失败时必须**熔断整个请求**，不允许静默失败
- LLM 调用失败时，最多重试 2 次（指数退避），之后返回降级响应
- 数据库连接池耗尽时，返回 503，不排队等待（避免雪崩）

### 4.3 安全

- 所有 Agent API 均需 JWT 认证（复用 hostess 现有 `JWTAuthBackend`）
- LLM 的 prompt 中不得明文出现客户完整身份证号、账户密码等高敏感字段
- Prompt Injection 防御：用户输入在传入 LLM 前，必须经过输入清洗（转义或隔离用户内容与系统指令）

### 4.4 可观测性

- 每个节点执行时间写入结构化日志（`node_id`、`duration_ms`、`status`）
- LLM 调用记录 token 用量，用于成本分析
- 提供 `GET /agent.metrics` 接口（仅 ADMIN 角色），返回近 24h 各节点 P95 耗时、错误率、Skill 调用分布

## 五、架构决策汇总

以下决策已由产品与架构团队确认，不在实现阶段反复讨论：

| 决策项 | 采用方案 | 理由 |
|---|---|---|
| 交互模式 | **多轮会话**，session 持久化 | 投资理财场景天然是对话式，上下文引用不可避免 |
| 人工审核机制 | **异步**，立即返回"待审核"状态 | 同步阻塞会长时间占用连接；审核可能跨工作日 |
| Node 4 输出 | **SSE 流式输出** | LLM 生成耗时长，流式显著改善用户体验 |
| Skill 选择策略 | **规则引擎**（意图 → Skill 映射表），非 LLM | LLM 选 Skill 不稳定，银行场景不可接受不确定性 |
| 并发 Skill 失败策略 | **读操作降级**（部分成功继续），**写操作全成功** | 读查询容忍部分结果，写操作绝不允许中间状态 |
| State 传递方式 | **显式字典**，节点间无隐性依赖，见设计文档 | 可调试、可审计、可复现 |
| 知识库检索时机 | **Node 3 阶段并发执行** | 与 Skill 并发，不增加链路时延 |
| 数据库 | **MySQL**（复用 hostess 现有技术栈） | 审计日志、会话、审核任务均写 MySQL |
| 向量数据库 | **ChromaDB** | 行内私有部署，数据不出行 |

## 六、业务约束与监管合规

- 本系统属于**辅助工具**，不具备"投资顾问"法律资质，输出内容**不构成投资建议**
- 所有 LLM 生成内容必须在界面上标注："本内容由 AI 生成，仅供参考，不构成投资建议"
- 本系统须满足《证券期货业网络安全管理办法》、《商业银行内部控制指引》中关于操作留痕、权限隔离的要求
- 审计日志满足监管机构抽查要求，支持按 `user_id`、`时间范围`、`意图类型` 检索
