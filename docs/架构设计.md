## 技术栈

| 层次 | 技术选型 |
|------|----------|
| Web 框架 | Starlette（ASGI，原生异步） |
| Agent 编排 | LangGraph + LangChain |
| LLM 接入 | ChatOpenAI 兼容接口（Qwen3 系列） |
| 向量数据库 | Milvus |
| 关系数据库 | MySQL（SQLAlchemy 2.x 异步引擎） |
| 认证 | JWT（python-jose，HS256） |
| 任务队列 | Huey（当前 MemoryHuey，可切换 Redis） |
| 日志 | loguru（异步 enqueue 模式） |
| 流式响应 | Server-Sent Events / NDJSON |

## 模块说明与设计模式

### 应用入口层

#### `main.py` — 应用工厂

采用**工厂模式**，`create_app()` 负责将路由、中间件、异常处理器、生命周期钩子组装到同一个 Starlette 实例上，便于测试时注入不同配置。

#### `routes.py` — 路由注册表

所有路由遵循**点号命名法**（`/auth.token`、`/agent.chat`），全部使用 POST 方法。这种风格的好处是接口语义清晰、便于网关层统一鉴权，不依赖 HTTP 动词语义，对 RPC 风格的企业内网调用更友好。

---

### core/ — 核心基础设施

#### `config.py` — 分环境配置

通过继承链 `BaseConfig → DevConfig / ProdConfig` 实现分环境配置，运行时通过环境变量 `DEBUG` 选择单例 `settings`。当前配置了两个 LLM 端点：

- `common`：qwen3-235b，用于常规对话
- `think`：qwen3-300b，用于深度推理节点

#### `lifespan.py` — 应用生命周期

使用 Starlette 的异步上下文管理器钩子，在服务启动时**按顺序**初始化所有基础设施（logger → db → llm_registry → graph_registry → milvus_registry），关闭时逆序释放。这保证了依赖顺序的正确性，也是 Starlette 替代 FastAPI `@app.on_event` 的推荐做法。

#### `llm_registry.py` / `graph_registry.py` / `milvus_registry.py` — Registry 单例模式

三个注册表均采用**单例 + 延迟初始化（Registry Pattern）**：

- 启动阶段一次性初始化，整个进程共享同一个 HTTP 连接池和向量库连接
- 业务代码通过 `llm_registry['common']`、`graph_registry['game']` 按名称取用，解耦了实例创建与使用
- 后续新增 LLM 模型或 Agent 图，只需在注册表中追加，不影响已有业务代码

#### `exceptions.py` + `handlers.py` — 统一异常体系

```
AppError
 ├── BusinessError(code, msg, data)   # 业务异常，会被序列化为 fail() 响应
 ├── BadRequestError                  # 400
 ├── UnauthorizedError                # 401
 └── ForbiddenError                   # 403

TokenExpiredError / TokenInvalidError  # JWT 专属
```

`handlers.py` 维护一张从异常类到处理函数的映射表，在 Starlette 的 `exception_handlers` 中统一注册，避免在每个视图中 try/catch。业务层只需 `raise BusinessError(BizCode.ITEM_NOT_FOUND)` 即可，框架层会自动格式化为统一响应结构。

#### `context.py` + `tracing.py` — 请求追踪

每个请求由 `RunIdMiddleware` 生成唯一 `run_id`，写入 `ContextVar`。loguru 的日志格式从 ContextVar 中读取 `run_id` 并注入每条日志，实现了**零侵入的请求级日志追踪**，无需在业务函数间手动传递追踪 ID。

#### `codes.py` — 业务状态码

`BizCode(IntEnum)` 每个枚举值携带 `(int_code, message)` 二元组，做到码值与描述文案集中维护，避免各处散落魔法数字。分段设计：2xxx 用户域、3xxx 商品域、4xxx 订单域、5xxx 支付域，后续扩展不冲突。

#### `queue.py` — 任务队列

当前使用 `MemoryHuey` 方便本地开发，生产环境切换为 Redis 只需修改一行实例化代码，Huey 的装饰器 API 不变。

---

### middleware/ — 中间件层

中间件栈由外到内执行，当前三层：

```
RunIdMiddleware          # 最外层：请求 ID 生成与透传
  └── CORSMiddleware     # 跨域处理
        └── AuthenticationMiddleware(JWTAuthBackend)  # JWT 解析，填充 request.user
```

`JWTAuthBackend` 解析成功后将 `JWTUser(user_id, username, roles)` 注入 `request.user`，失败则注入匿名用户（不抛异常），真正的拦截由 `core/auth.py` 的装饰器在视图层按需执行，实现了**认证与鉴权的分离**。

---

### utils/ — 工具模块

全部为**纯函数**，无副作用，无外部依赖注入：

| 模块 | 职责 |
|------|------|
| `jose.py` | JWT 双 Token（Access 2h + Refresh 7d）生成与验证 |
| `serial.py` | JSON 扩展编码（datetime / Decimal / UUID / bytes） |
| `arrow.py` | 统一时间工具，避免各处 `datetime.now()` 格式不一 |
| `rand.py` | 随机 token 生成（UUID hex 截取） |

---

### domains/ — 业务域

采用**三层架构（Layered Architecture）**，每个业务域独立一个子包：

```
views.py       # 视图层：解析请求参数、调用 service、返回响应（不含业务逻辑）
service.py     # 业务层：编排业务流程、跨 repository 组合数据
repository.py  # 数据层：仅执行 SQL，返回原始数据
errors.py      # 领域异常：继承 BusinessError，携带领域专属状态码
tasks.py       # 异步/定时任务：Huey 装饰器标注，独立于请求链路
```

`items/errors.py` 演示了领域专属异常的定义方式：`ItemNotFoundError`、`StockInsufficientError` 直接继承 `BusinessError` 并预设 `BizCode`，业务代码只需 `raise ItemNotFoundError()` 即可，无需在 service 层关心如何序列化。

---

### agents/ — Agent 应用层

每个 Agent 应用为 `agents/` 下的独立子包，当前已实现 `game/` 作为多 Agent 范式的参考实现。

#### 设计模式：Supervisor 多 Agent

```
用户输入
   │
   ▼
supervisor（LLM 路由，结构化输出 RouterOutput）
   │
   ├─→ agent_a（工具：search_web + calculate）
   ├─→ agent_b（工具：calculate + query_database）
   └─→ agent_c（工具：search_web + query_database）
         │
         ▼
      tool_node（ToolNode 执行工具调用）
         │
         └─→ 回到对应 agent 节点（循环直到无 tool_calls）
```

- **supervisor** 作为中央调度者，使用结构化输出（`RouterOutput`）确保路由决策可解析，避免自由文本带来的不确定性
- **各 Agent 节点**绑定不同工具集，职责分离，易于扩展
- **图在启动时编译一次**（`build_game_graph()`），运行时只做状态流转，无重复构建开销

#### 流式响应链路

```
chat_stream_and_save()    # service 层：加载历史 → 流式调用图 → 保存对话
   └── chat_stream()       # 过滤 on_chat_model_stream 事件，跳过 supervisor 内部输出
         └── graph.astream_events()   # LangGraph 原生异步事件流
                                       # views 层：yield NDJSON 行到客户端
```

每行输出格式为 `{"text": "<token>"}` 的 NDJSON，客户端可逐行解析，实现逐字流式显示。

## 待完善的企业级功能模块

以下模块在当前框架结构内有良好的扩展点，均可在不破坏现有设计的前提下逐步落地。

---

### 1. 统一身份认证（SSO 接入）

**现状**：`auth/` 域实现了基于用户名 + 密码的本地认证，JWT 双 Token 机制已就绪。

**待完善**：
- 接入企业 OIDC / OAuth 2.0 Provider（如 Keycloak、Azure AD、飞书开放平台）
- 在 `JWTAuthBackend` 中支持解析来自 IdP 的 token，或实现 token 交换（IdP token → 本系统 JWT）
- 支持 SSO 单点登出（token 黑名单，需 Redis 支持）
- Refresh Token 轮转（Refresh Token Rotation），防止 token 泄露后的长期滥用

**扩展点**：`src/domains/auth/`、`src/middleware/guards.py`、`src/utils/jose.py`

---

### 2. 细粒度权限管理（RBAC / ABAC）

**现状**：`permission_required(scope)` 装饰器通过比对 `JWTUser.roles` 列表实现简单 RBAC，roles 在登录时硬编码写入 token。

**待完善**：
- 持久化角色 / 权限表（`roles`、`permissions`、`role_permissions`、`user_roles`），支持动态配置
- 实现权限缓存（Redis），避免每次请求查库
- 扩展为 ABAC（基于属性的访问控制），支持"某用户只能操作自己部门的数据"等细粒度策略
- 管理后台 API：角色 CRUD、权限分配、用户-角色绑定

**扩展点**：`src/core/auth.py`、`src/domains/auth/`、新增 `src/domains/rbac/`

---

### 3. RAG 知识库权限管理

**现状**：`milvus_registry.py` 在启动时预加载指定 Collection，`demos/milvus.py` 演示了基础检索流程，但无文档级权限控制。

**待完善**：
- **文档元数据权限字段**：在 Milvus 向量记录中增加 `tenant_id`、`department_id`、`visibility`（public / department / private）字段，检索时注入过滤条件
- **Collection 隔离策略**：不同业务域 / 租户使用独立 Collection，注册表按权限动态加载
- **文档管理 API**：
  - 文档上传（分块 + 嵌入 + 入库）
  - 文档更新（先删旧向量再重新嵌入）
  - 文档下线（软删除 + 向量删除）
  - 文档审核流程（草稿 → 待审 → 已发布）
- **嵌入模型管理**：支持多嵌入模型共存，不同知识库可配置不同模型

**扩展点**：`src/core/milvus_registry.py`、新增 `src/domains/knowledge/`

---

### 4. Agent 高可用与可观测性

**现状**：LangGraph 图在单进程内运行，流式输出通过 NDJSON 返回，无重试机制和监控埋点。

**待完善**：

#### 4.1 高可用
- **LLM 调用重试与降级**：在 `llm_registry` 层封装重试策略（指数退避），主模型不可用时自动切换备用模型
- **超时控制**：为每个 LangGraph 节点设置调用超时，防止单节点阻塞整个图
- **会话恢复**：利用 LangGraph 的持久化 Checkpointer（当前可能用内存），切换为数据库 Checkpointer，支持服务重启后恢复未完成的图执行
- **任务队列化**：长耗时 Agent 任务从 HTTP 请求链路移到 Huey 任务队列，客户端通过轮询或 WebSocket 获取结果

#### 4.2 可观测性
- **结构化日志**：当前 loguru 日志已注入 `run_id`，可进一步增加 `session_id`、`agent_name`、`node_name`、`token_usage` 等字段，对接 ELK / Loki
- **LangSmith / 自建 Trace 系统**：为每个 LangGraph 节点埋点，记录输入输出、耗时、token 消耗，支持调用链回放与问题排查
- **指标暴露**：新增 `/metrics` 端点（Prometheus 格式），暴露请求 QPS、Agent 调用成功率、LLM 响应延迟、队列积压深度等指标

**扩展点**：`src/core/llm_registry.py`、`src/agents/`、`src/core/logger.py`、`src/routes.py`

---

### 5. 多租户与数据隔离

**现状**：认证体系中有 `user_id`，但无租户（`tenant_id`）概念，所有用户共享同一数据库和向量库。

**待完善**：
- 在 `JWTUser` 中增加 `tenant_id` 字段，登录时从数据库加载
- 数据库层在 `repository` 基类中自动注入 `tenant_id` 过滤条件（防止越租户查询）
- Milvus 向量检索自动过滤租户 partition 或 metadata 字段
- 租户级配置（每个租户可配置不同 LLM 模型、知识库、Agent 流程）

**扩展点**：`src/middleware/guards.py`、`src/core/auth.py`、各 `repository.py`

---

### 6. Agent 审查与人工介入

**现状**：`routes.py` 中已预留 `/agent.review.list`、`/agent.review.approve`、`/agent.review.reject` 路由，但对应的 `agent` 域视图尚未实现。

**待完善**：
- 基于 LangGraph `interrupt()` 机制在关键节点暂停图执行，等待人工确认
- 审查任务持久化（记录待审内容、审查人、审查时间、审查意见）
- 消息推送（审查任务创建后通过企业 IM / 邮件通知相关人员）
- 审查超时自动处理策略（超时自动拒绝或自动通过）

**扩展点**：`src/routes.py`（路由已预留）、新增 `src/domains/agent/` 或 `src/agents/review/`

---

### 7. 任务队列生产化

**现状**：Huey 使用 `MemoryHuey`，仅支持单进程，重启后任务丢失。

**待完善**：
- 切换为 `RedisHuey`，任务持久化，支持多 Worker 横向扩展
- 实现任务状态查询 API（`/task.list`、`/task.get` 等，测试脚本已准备好）
- 任务优先级队列（Agent 任务高优先于导出任务）
- 死信队列：超过最大重试次数的任务转入死信队列，支持人工重放

**扩展点**：`src/core/queue.py`、新增 `src/domains/tasks/`

---

### 8. API 网关与限流

**现状**：Starlette 应用直接暴露，无限流、熔断保护。

**待完善**：
- 接口级速率限制（基于 `user_id` 或 `tenant_id`，存储于 Redis）
- LLM 调用配额管理（按租户 / 用户限制每日 token 消耗）
- 熔断器（Circuit Breaker）：LLM 服务连续失败时快速失败，避免级联超时
- 请求签名验证（内部服务间调用）

**扩展点**：`src/middleware/`、新增限流中间件
